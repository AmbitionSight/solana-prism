# Solana Prism — 先攻破，再揭晓（教学重写设计）

> 状态：已与用户逐节确认（§3–§6 两节经用户批准），待复核后转实施计划。
> 日期：2026-10-10
> 适用仓库：`solana-prism`（分支 `feat/prism`）
> 前置：两个合约已部署到 testnet，31 个 vault 池已建成，真实攻击与拒绝均已取证。

## 1. 问题：为什么现在这版教不会人

用户看完的实际反馈：「演示性不强」「没有教育意义」「没有场景」。三句话指向同一件事。

现版本是一个**观看**的演示：六步动画把 `missing signer check` 拆开讲清楚。它诚实、做工扎实，但它要求观众**被动接受一个结论**。看完之后观众记住的是「有个按钮点了数字会变」，不是一个可以带走的能力。

三处具体的缺陷：

1. **没有场景。** 没有受害者、没有后果、没有角色。vault 是演示造的，余额变化只是一个数字，面板自己还写明「不涉及 lamport 转移」。赌注是零，注意力就留不住。
2. **「冒充」这一步是隐形的。** 漏洞的核心是「签名没被要求」—— 而**没有的东西天生看不见**。观众从没做过任何像攻击的动作，只是点了个按钮，所以无从体会那一步。
3. **只有一个例子。** 一个例子教会的是一行代码，不是一个类别。观众离开时记住的是「`AccountInfo` 不行」，而不是「手写地址检查代替不了认证」—— 换个写法他就认不出来了。

## 2. 目标与验收标准

**目标：让观众获得可迁移的能力，不是一次性的理解。**

判定标准（用户选定）：**给他一段没见过的合约，他能自己指出哪里有同类漏洞。**

这条标准反推出三个硬要求：

- 必须**先判断、后被纠正**（预测—揭晓），不能先被告知
- 必须有**多个变体**（跨实例才能形成类别）
- 必须由**真实链**给判决（观众信的是链，不是我们的文案）

## 3. 场景

**用户选定的角色：审计员，上线前签字。**

丢给你几份合约，你对每一份下判断「能上主网 / 会被绕过」，链上给你真实判决。

但审计员的真实工作不是读报告，是**动手试**。所以第一幕的结构是：**先亲手攻破一个，再去看清为什么能被攻破。**

```
第一幕  一个合约：你亲手攻破它，然后看清它为什么能被攻破
第二幕  三份合约：你必须找出哪份能被攻破        ← 检验迁移
```

## 4. 第一幕：真实化的开场

### 4.1 开场展示**链上那份合约的真实全文**

现在开场展示的是一段**节选**：真的 `Withdraw` 结构 + 真的 `withdraw` 函数，但抽掉了 `initialize`、`Vault`、`declare_id!`，注释是为 i18n 另写的。

改成展示 `frontend/public/source/prism_vulnerable.rs.txt` 的**逐字全文** —— 这份文件已经有守卫测试保证与 `contract/` 逐字节一致，所以展示的不是「我们抄了一遍」，而是**已经受保护的那一份**。

顶部加一行状态栏：

```
prism_vulnerable
7SdcJctnNWx1CPrfJr5MR8jWgDLtW173FoYyCm8rP8U2
● 已在 testnet 上运行
```

**代价与解法**：现在的代码列表注释随语言切换（中文读者友好）。逐字文件没有中文注释。解法是把中文说明放进**旁注栏**，不塞进代码 —— 「这是真文件」与「中文读者看得懂」两个都要。

**阶段区域映射**（`CODE_REGIONS`）需要按真实文件的行号重做。当前映射针对节选，行号全部会错位。对照 `contract/programs/prism_vulnerable/src/lib.rs`：

| 阶段 | 真实文件行 |
|---|---|
| S2 Accounts | 53–55（`pub struct Withdraw` 头 + `vault` 字段） |
| S3 Declaration | 56–57（注释 + `pub authority: AccountInfo<'info>,`） |
| S1 Instruction | 30（`pub fn withdraw(...)`） |
| S4 Manual Check | 32–36（注释 + `require!` 整块） |
| S5 State Change | 37（`vault.balance -= amount;`） |

### 4.2 交易卡片使用**真实地址**

现在无钱包时卡片显示编造的 `7xKm…9mPQ` / `ADMiN…x7wQ`（`TxCard.tsx:52-65`）。也就是说，整个演示最有说服力的那一幕（「地址在场、签名缺席」）在默认路径下是**布景**。

改成：**无钱包也读链。** 页面加载时用现成的 `nextFreshVault` 找下一个新鲜 vault，卡片渲染真实的程序地址 / vault 地址 / 管理员地址。

于是有无线包的区别变成：**没钱包 = 你能看见这笔真实交易；有钱包 = 你能真的发出去。**

**技术风险**：`tools/shoot.mjs`（无头浏览器走查）依赖无钱包路径的确定性。解法是 **RPC 不可达时回退到内置常量**，渲染形状完全一致。走查必须仍然全绿（实测确认，不假设）。

### 4.3 新的步骤序列

现行序列是「标题 → 节选代码 → 拆解 → 层叠 → 攻击 → 验证」，拆解与层叠**发生在攻击之前**。

新序列把拆解与层叠移到**攻击之后**（它们现在是「揭晓」，不是「教材」）：

| # | 步骤 | 内容 | 从哪来 |
|---|---|---|---|
| 1 | 标题 | 一句话引入 | 现有 `Step1Title` |
| 2 | 合约 | 链上那份的**真实全文** + 状态栏 + 中文旁注 | 改写 `Step2Code` |
| 3 | 攻击计划 | 两个问题，观众作答 | **新增** |
| 4 | 揭晓 | 执行 → 拆解 → 层叠 → 裂缝 → 穿透 → 判决 | 复用现有步骤 3–5 的动画 |
| 5 | 证据 | 真实签名 / Solscan | 现有 `VerifyPanel` |

关键结构变化：**步骤 3–4 的动画不再自动播放**，它们由步骤 3 的执行触发。`AUTO_ADVANCE_MS` 因此只覆盖步骤 1–2。

## 5. 第一幕：攻击计划与执行

**核心机制：先下注，再执行。** 不给「攻击」按钮，而是让观众说清自己的攻击计划。

### 5.1 第 2 步 —— 观众填计划

看到合约与部署信息后，回答两个问题：

- 「你要把**谁**的地址填进 `authority`？」→ [管理员的地址] / [你自己的地址] / [vault 的地址]
- 「这笔交易上**必须**有谁的签名？」→ [只要我自己的] / [必须有管理员的] / [两个都要]

三样信息（程序地址、vault、管理员地址）在这一步都标为**公开信息** —— 这句标注会在揭晓时变成关键。

### 5.2 第 3 步 —— 忠实执行，链上判决

按观众的计划组装交易，用其钱包真实发出（`skipPreflight`，理由同现有 `solanaChain.ts`）。

**两个分支都有教学价值**：

- `authority` 选错 → 链上拒绝 `RequireViolated` → 学到：**地址检查是真的存在的**
- `authority` 选对 → 成功，余额 1000 → 500 → 学到：**它只查地址，不查签名**

### 5.3 无钱包的访客也能走完整条路（用户确认）

**计划表单对所有人开放。** 大多数访客不会连接钱包，如果这条教学路径要求钱包，就等于对大多数人关闭。

两种执行方式，同一个结论：

| | 无钱包 | 有钱包 |
|---|---|---|
| 填计划 | ✅ | ✅ |
| 执行 | 按计划播放动画（用**真实**地址） | **真的发出去** |
| 揭晓 | ✅ 同样的对照 | ✅ 同样的对照 |

于是「连接钱包」从一个**门槛**变成一次**升级** —— 它不再决定你能不能学，只决定你能不能亲手做。

### 5.4 「Vulnerable / Fixed」切换在第一幕中移除（用户确认）

旧版第 5 步有一个在漏洞版与修复版之间切换的开关。第一幕移除它。

理由：第一幕的叙事是**攻破一份合约，再看清为什么**。一个并行的「或者你也可以攻击已修复的那份」会把这个叙事打散。

修复版能挡住攻击这件事**不作废** —— 它移到揭晓里，作为结论后的验证（`VerifyPanel` 已经在展示那笔真实的拒绝交易）。

## 6. 第一幕：揭晓

**原则：不解释给观众听，把证据摆出来让观众自己对上。**

### 6.1 先摊开刚发出去的真实交易

```
accounts:    vault      7v6Pm…peu5     ← 池里的真实 vault
             authority  DMkwn…GU7T     ← 管理员的地址（谁都能知道）
signatures:  你         ✓ e3f9…
             ADMIN      ✗             ← 这一栏不存在
```

### 6.2 对照观众在第 2 步下的注（本设计的支点）

观众不是被「告知」，是被**自己的答案**打脸：

> **你说的**：这笔交易必须有管理员的签名
> **交易的真相**：上面只有一个签名，是你的
> **结果**：vault 里的 1000 已经变成 500

若 `authority` 选错，得到的是另一句：

> **你说的**：把你自己的地址填进去就行
> **链上拒绝**：`RequireViolated`
> **说明**：地址检查**是真的存在的** —— 这正是这个漏洞比它看起来更狡猾的原因

### 6.3 然后回答「为什么它拦不住」

此时才放动画。现有的拆解 / 层叠 / 裂缝 / 穿透动画**全部复用**，位置从「教材」变成「答案」。

```
阶段 1  Instruction          withdraw(ctx, amount)
阶段 2  Accounts             vault · authority
阶段 3  Account Declaration  authority: AccountInfo<'info>   ← 什么都没要求
阶段 4  Manual Check         require!(vault.authority == ...) ← 比对两个公开的值
阶段 5  State Change         vault.balance -= amount
```

题眼（最后一句）：

> 阶段 4 那行 `require!` 比的是两个**公开的值**。它从来没有问过「谁签了名」。
> **如果阶段 3 写的是 `Signer<'info>`，运行时会在你的交易还没走到阶段 4 之前就把它拒之门外。**

### 6.4 证据段

现有 VerifyPanel 保留：真实签名、Solscan 链接、修复版拒绝。它现在是从数据推导措辞的，无需改动逻辑。

## 7. 第二幕：找出哪份能被攻破

给观众**三份**合约，它们**长得几乎一样**，只有账户声明不同。对每一份下判断（「能上主网 / 会被绕过」），并实际尝试。链上给判决。

程序里承载 6 个变体（下表），但每轮只呈现其中 3 份：**一份有漏洞、两份看起来像修好了但其实写法不同**。固定这三份，不随机 —— 观众之间要能讨论同一道题。

**为什么必须有第二幕**：第一幕给出一个实例，第二幕把「一个实例」逼成「一个类别」。这才是「迁移到陌生代码」这个验收标准的直接训练。

### 7.1 技术方案：一个程序，多个指令

一个 Anchor 程序可以有任意多个指令，每个指令有自己的 `#[derive(Accounts)]`。所以**一次部署**就能放下全部变体。

候选变体（每个是一个 `withdraw` 变体）：

| # | 声明 | 预期 |
|---|---|---|
| 1 | `authority: AccountInfo` + `require!(address)` | 可攻破（现有漏洞版） |
| 2 | `authority: Signer` | 安全（现有修复版） |
| 3 | `authority: AccountInfo` + `require!(address && is_signer)` | 安全，但写法不同 |
| 4 | `authority: AccountInfo`，无任何检查 | 可攻破，且更明显 |
| 5 | `authority: UncheckedAccount` + 手写检查 | 视检查内容而定 |
| 6 | `authority: AccountInfo` + PDA 推导 | 安全，第三种机制 |

变体 3 和 5 是设计的关键：它们**看起来像手写检查**，但结果不同 —— 直接破除「手写检查也行」这个误解。

### 7.2 ⚠️ 成本问题（待用户决定）

第二幕需要一个**新的部署**（新程序，或多指令变体）。按当前 SOL 价格：

- 一个程序约 169 KB → programdata 租金约 **0.86 SOL**
- 部署峰值 = buffer + programdata ≈ **1.72 SOL**（buffer 事后退还）
- **当前部署钱包余额 1.276 SOL —— 不够**

选项：

- **A. 追加约 0.5–1 SOL**，部署变体程序
- **B. 用现有两个程序**（漏洞版 / 修复版）做三份合约中的两份，第三份以「代码呈现 + 揭晓解释」的方式给出 —— 零成本，但第三份没有链上判决
- **C. 第二幕推迟**，先把第一幕做完做好，再决定

**建议 C → 再 A。** 第一幕本身就是完整、可交付的一跃，且它承载了用户全部的即时反馈（真实化 + 先攻破 + 揭晓）。第二幕是加法。

## 8. 不做（YAGNI）

- 不做自由输入式的攻击构造（自己粘地址）—— 劝退，且不增加迁移价值
- 不做后端 / 中继服务 —— 所有能上链的动作都用观众自己的钱包
- 不重录 `walkthrough.mp4` 与 `contact-sheet.png`（除非第一幕完成后用户要求）
- 不改 `lib/geometry.ts`、`lib/keyframes.ts` 的坐标系
- 不改合约的指令语义（`contract/` 逻辑零改动）
- 不做移动端适配

## 9. 验收标准

1. `npm test` 全绿（现有 246 项 + 新增项）
2. `npm run build`（`tsc -b && vite build`）通过
3. `tools/shoot.mjs` 在无钱包状态下全绿（含 RPC 不可达时的回退路径）
4. 开场展示的合约文本与 `frontend/public/source/prism_vulnerable.rs.txt` 逐字一致，且有守卫断言
5. 无钱包时交易卡片显示**真实**程序地址与管理员地址（RPC 可达时）
6. 攻击计划的两个分支都能走通并有各自的揭晓文案
7. 真实攻击在 testnet 上跑通一次，余额变化可见

## 10. 风险

| 风险 | 处置 |
|---|---|
| 展示真实全文后，`CODE_REGIONS` 行号错位 → 阶段高亮全错 | §4.1 已列出真实行号；实施时加守卫断言被框的行文本 |
| 无钱包读链导致 `shoot.mjs` 变慢/失败 | 回退常量；实施后实测走查，不假设 |
| 逐字文件丢失中文注释 → 中文读者体验下降 | 旁注栏承载中文说明，不塞进代码 |
| 第二幕需要追加 SOL 而用户不想追加 | §7.2 选项 C：第二幕推迟，第一幕独立成立 |
| 改动面大（开场、卡片、交互、揭晓） | 按实施计划分任务，每任务独立可验证 |
